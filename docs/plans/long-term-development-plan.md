# Atoman 前端长期开发计划

- 状态：草案
- 范围：`Atoman-Frontend` 的产品交付、质量、发布，以及与 `Atoman-Backend`、`Atoman-iOS` 的协作契约
- 规划周期：6 至 9 个月，每月复盘
- 最后更新：2026-08-20

## 1. 产品方向

Atoman 应当成为一个可靠的内容平台，由三个相互支撑的层次组成：

1. **Feed 是日常入口。** 用户能发现来源、订阅、搜索、阅读，并持续回到对自己有用的内容流。
2. **Blog 与 Studio 是创作核心。** 创作者能在一个工作区写作、管理、定时发布、维护内容，并理解内容表现。
3. **音乐、播客、视频与社区模块沉淀差异化内容。** 它们应共享可靠的媒体、互动和权限基础，而不是分别演变成孤立产品。

当前前端的功能面已经很广，因此下一阶段的重点不是增加内容分类，而是提升可靠性、产品聚焦和运营能力。

## 2. 范围与边界

### 前端职责

- Vue 应用行为、响应式界面、无障碍、SEO 元数据和客户端性能。
- API 客户端契约、请求恢复、上传状态恢复、路由稳定性和产品埋点。
- 单元、集成和浏览器端测试。
- Cloudflare Pages 配置、前端 Docker 镜像和前端发布物。

### 跨仓库依赖

- `Atoman-Backend` 是 API 契约、授权、数据库迁移、媒体后台任务、部署编排和网关路由的唯一权威。
- `Atoman-iOS` 消费同一套公开 API 契约。任何用户可见的数据模型或授权变化，都必须在实现前评估 iOS 兼容性。
- 跨端改动在编码前必须具备书面 API 契约、后端迁移策略、前端错误状态设计和发布顺序。

### 本周期明确不做的事

- 不新增顶层内容模块。
- 权限、限流、审计和文档未稳定前，不开放公共 API 或浏览器扩展。
- 不为了视觉重构替换已正常工作的产品流程。
- 不把前端 mock 当作已完成的跨端能力。

## 3. 当前基线

前端已具备 Feed、Blog、音乐、论坛、辩论、时间线、播客、视频、Studio、设置和通知的公开或登录后路由。主要闭环已存在，但各模块的运行成熟度不同。

| 领域 | 当前方向 | 规划含义 |
| --- | --- | --- |
| Feed | 已有发现、订阅、阅读、收藏、稍后读、推荐和来源管理。 | 将 Feed 作为第一产品优先级；现有 P0 是分组规则、探索到订阅的转化和全文检索质量。 |
| Blog 与短话 | 已有阅读、创作、互动、版本、定时发布和短话。 | 优先完成编辑器可靠性，并将创作者管理收敛到 Studio。 |
| Studio | 已有仪表盘、内容、合集、互动、数据、设置和编辑器路由。 | 将其稳定为 Blog、播客、视频唯一的创作管理工作区。 |
| 音乐 | 已有发现、档案、播放、歌词、导入、编辑、收藏和历史。 | 优先处理加载行为、可恢复操作和可观测性，不继续扩张发现页面。 |
| 播客与视频 | 已有发现、订阅、收藏、创建、详情和编辑器路由。 | 补齐媒体生命周期，并复用共享的失败恢复模式。 |
| 社区 | 已有论坛、辩论、时间线、评论和通知。 | 在扩大公开参与前先补齐治理和审核能力。 |
| 用户设置 | 核心账户路径存在，部分偏好项仍未开放。 | 只有在 API 与隐私模型完整时才替换占位界面。 |

## 4. 交付原则

1. **先闭环，再扩张。** 一个功能必须覆盖加载、空状态、错误、重试、移动端、权限、埋点和测试，才算完成。
2. **优先复用生命周期。** 上传、处理、发布、互动和删除应尽量使用共享基础设施。
3. **异步工作必须可见且可恢复。** 后台导入和长请求不能让用户无从判断，也不能阻塞无关编辑。
4. **先测量，再优化。** 在决定数值目标前，先获得性能与转化的基线数据。
5. **客户端契约必须明确。** 列表和恢复路径不应依赖偶然的重型详情接口；需要摘要或状态接口时应明确增加契约。
6. **小批、可回滚地发布。** 高影响改动需要功能开关、迁移安全的契约、发布版本和清晰的回滚路径。

## 5. 阶段 0：发布与运营基线

周期：第 0 至 3 周

**目标：** 将现有广泛的功能面转化为可持续迭代的安全发布流程。

### 5.1 发布候选收敛

- 将大批进行中改动拆成可审查、可独立发布的候选。每个候选必须包含实现、相关测试和用户可见行为说明。
- 优先处理当前活跃的编辑器、路由恢复、通知、Markdown 渲染和设置改动。
- 不在同一候选中混入无关视觉清理、路由调整和 API 行为变化。
- 每次用户可见变化维护简短发布说明。

### 5.2 CI 与测试门槛

- 所有 Pull Request 保持强制类型检查和生产构建。
- 保留 Pull Request 的关联单测与推送后的全量单测。
- 为临时或预发布兼容环境增加 Playwright 冒烟测试，至少覆盖：
  - 登录和第一个登录后路由；
  - Feed 订阅与文章阅读；
  - Blog 新建或编辑与草稿恢复；
  - Studio 内容访问；
  - 音乐播放和导入恢复。
- 在夜间任务和发布前执行完整浏览器套件。
- 接入覆盖率报告。先建立基线，再逐步提高 API transport、路由守卫、编辑器持久化、授权和上传恢复的阈值。

### 5.3 发布拓扑定案

将两条交付路径明确命名，而不是把它们当作可互换的生产方案：

- **官方托管 Web：** Cloudflare Pages 服务公开前端。
- **自托管 Web：** 前端 Docker 镜像带版本号，由后端仓的部署 Compose 消费。

两条路径必须来自同一 Git SHA，并暴露相同的 `VITE_APP_VERSION`。发布流程必须说明环境变量、API 兼容性、回滚、缓存失效和责任归属。

### 5.4 可观测性与支持能力

- 增加前端错误上报，包含发布版本、路由、浏览器类型和请求关联信息；不得发送内容正文、凭据或个人数据。
- 记录导航性能、最大内容绘制、路由分块加载失败、上传恢复和 API 失败。
- 统一用户可见失败状态：明确下一步、安全时提供重试，且不存在无终止的加载状态。
- 建立 API 错误率、客户端错误率、路由恢复刷新、导入失败率和发布采纳率的运营看板。

### 验收标准

- 每个发布候选均通过类型检查、生产构建、相关单测和浏览器冒烟测试。
- 可通过前端版本回滚，无需修改源码。
- 团队能把用户报告关联到发布版本、路由和失败操作。
- 不再存在只有某个工作树保存的大型无归属进行中改动。

## 6. 阶段 1：将 Feed 建设为日常入口

周期：第 1 至 2 个月

**目标：** 让用户更容易发现、组织、搜索和行动于订阅内容，提升获客和回访。

### 6.1 产品工作

#### 分组自动规则

- 支持按来源、标签、主题、语言和更新频率定义分组。
- 展示来源为何属于某个分组，并在保存前预览规则影响。
- 支持手动覆盖，但不得悄然删除规则带来的成员关系。

#### 探索到订阅的转化

- 为推荐频道和外部来源提供可理解的推荐理由。
- 支持单个和批量订阅，并在成功后立即提供有价值的下一状态。
- 用户从详情返回时保留探索筛选条件和滚动位置。

#### 全文检索质量

- 定义查询解析、筛选、排序、高亮、空结果行为和结果新鲜度。
- 在暴露高级排序控制前，先增加后端索引和稳定响应契约。
- 采集隐私安全的查询结果信号，例如打开结果、订阅来源、改写查询。

#### 阅读习惯闭环

- 明确未读、稍后读、收藏和星标之间的关系。
- 只有在持久化语义确定后，才增加阅读偏好设置。
- 阅读事件上报必须异步，不能阻塞文章打开。

### 6.2 后端与数据依赖

- 规则评估 API，包含校验、预览和幂等变更行为。
- 搜索契约，明确分页、筛选、排序、片段和索引。
- 来源推荐和订阅 API，明确当前用户相关字段。
- 区分用户操作事件与内容抓取任务的事件模型。

### 6.3 前端验证

- 为规则序列化、查询同步、排序和状态恢复编写单测。
- 浏览器测试覆盖首次订阅、分组阅读、打开搜索结果、收藏/星标和未登录边界。
- 对高密度来源管理界面进行响应式和键盘操作审查。

### 验收标准

- 新用户能在一次会话内发现来源、订阅、阅读，并回到个性化 Feed，且不丢失上下文。
- 搜索拥有可测的相关性和延迟基线，以及明确的改进目标。
- 分组规则可理解、可撤销，不会意外隐藏已订阅内容。

## 7. 阶段 2：创作流程与 Studio 收敛

周期：第 2 至 4 个月

**目标：** 让创作可靠，并让 Studio 成为 Blog、播客和视频唯一的管理界面。

### 7.1 产品工作

#### Blog 编辑器可靠性

- 完成富文本与 Markdown 编辑器边界，同时保留已有文档语义。
- 保证草稿持久化、刷新或保存失败后的恢复、版本历史、预览、封面管理和资源上传恢复。
- 覆盖破坏性操作、冲突恢复、定时发布，以及编辑中权限丢失等场景。

#### Studio 收敛

- 将内容、合集、互动、数据和设置统一到 Studio。
- 在 Blog、播客、视频之间使用单一当前频道模型。
- 只有在重定向、权限、埋点和迁移路径验证后，才移除重复的创作者入口。

#### 创作者控制能力

- 完成合集管理、内容生命周期筛选、定时发布、版本恢复和互动处理。
- 在增加图表前，先明确哪些数据能够帮助创作者采取行动。
- 只有在界面可以正确保存、显示和撤销设置时，才替换“尚未开放”的偏好项。

#### 社区治理

- 为公开创作和评论增加举报、审核队列、所有权校验、审计事件和限流。
- 申诉和内容可见性状态必须由后端强制执行，不能只在客户端隐藏。

### 7.2 后端与数据依赖

- 稳定的 Studio 频道、合集、内容生命周期、定时、互动和数据契约。
- 保留旧频道、合集、内容、订阅关系和标识符的迁移方案。
- 可能并发编辑时使用乐观并发或版本感知的冲突处理。
- 在扩大高频公开创作前，完成审核与审计数据模型。

### 7.3 前端验证

- 使用浏览器自动化验证编辑器恢复和冲突。
- 为每个 Studio 入口编写路由与 feature gate 测试。
- 端到端覆盖新建、编辑、定时、发布、恢复和删除。

### 验收标准

- 创作者无需依赖旧管理路由，即可从 Studio 管理三种创作模块的内容。
- 中断编辑可恢复，且不会无提示覆盖用户内容。
- 定时和恢复后的内容拥有所有者可见、可审计的生命周期。

## 8. 阶段 3：媒体可靠性与共享生命周期

周期：第 4 至 6 个月

**目标：** 让音乐、播客和视频在慢网络、大文件、后台处理和重复操作下仍然可靠。

### 8.1 产品工作

#### 音乐可靠性

- 恢复路径使用轻量摘要接口；重型档案详情只用于用户显式打开的详情页。
- 导入会话必须可恢复，具有服务器权威状态、清晰处理进度、重试选项和修复流程。
- 为播放、队列切换、歌词编辑、上传完成和导入失败路径增加埋点。

#### 播客与视频生命周期

- 统一上传、处理、草稿编辑、发布、播放/观看、订阅、收藏和重试状态。
- 后端允许时，编辑器应能在上传或处理中继续发挥作用。
- 状态文案只解释用户下一步，不暴露内部 worker 细节。

#### 共享媒体基础设施

- 复用上传会话、轮询与退避、取消、状态展示、对象存储错误归一化和资源选择能力。
- 在 API 文档中定义状态机转移，客户端只展示当前状态下有效的操作。

### 8.2 后端与数据依赖

- 后台任务状态契约，包含单调阶段、重试策略、终止错误原因和授权校验。
- 上传和提交操作使用幂等键或会话身份。
- 使用轻量档案与状态接口，避免不必要的关联预加载。
- 对象存储失败处理和清理保证。

### 8.3 前端验证

- 浏览器测试覆盖上传中断、离开再返回、刷新恢复、重试、防重复提交和慢网络渲染。
- 为媒体状态转移和显示工具编写单测。
- 为音频播放完成设备和 MediaSession 验证。

### 验收标准

- 用户能理解并恢复媒体处理失败，不会创建重复内容。
- 慢详情请求不会阻止已可恢复草稿的编辑。
- 音乐、播客、视频在共享领域规则上呈现一致的媒体生命周期。

## 9. 阶段 4：生态与增长

周期：第 6 至 9 个月

**目标：** 在不削弱隐私、可靠性和审核能力的前提下，将已稳定的核心扩展到外部来源和客户端。

### 9.1 产品工作

1. 在来源归属、版权、删除、去重和署名策略获批后，接入 Newsletter、YouTube 和其他来源。
2. 只有在用户可控制偏好、频率、来源范围和生成内容留存时，才增加文章与来源摘要。
3. 准备带有版本、认证 scope、限流、分页策略、审计日志和公开文档的 API。
4. 浏览器扩展必须建立在公共 API 上，不能创建私有的临时端点集合。
5. 通过共享的收藏、历史、订阅、通知和播放进度契约，提升移动 Web 与 iOS 的阅读连续性。
6. 将动态 SEO 元数据扩展至公开内容详情，同时保护未发布、私密和管理路由不被索引。

### 验收标准

- 外部集成使用稳定、文档化的契约，且停用时不会损坏用户资料库。
- 公共 API 具备 scope、限流、可观测性和版本管理。
- 跨设备阅读和媒体状态拥有清晰的冲突与隐私规则。

## 10. 持续质量要求

### 无障碍

- 新增或修改流程必须支持键盘导航、可见焦点、语义标题、正确对话框行为、实时区域提示和表单错误。
- 在浏览器测试流程中运行自动化无障碍检查，并手动审查编辑器、播放器、上传、表格和抽屉交互。
- 尊重减少动效偏好，并在移动、平板和桌面尺寸下保持可用布局。

### 性能

- 建立公开入口、登录后模块入口、路由分块失败和 API 响应影响的基线。
- 在获得基线后设置逐路由性能预算，而不是只依赖全局 chunk 警告。
- 持续进行路由级拆分、非关键请求延后、过期请求取消，并在列表与恢复界面使用摘要接口。

### 安全与隐私

- 授权必须由后端 API 强制执行；前端 feature gate 仅用于体验控制，不能作为安全边界。
- 每个公开 mutation 必须检查 CSRF/认证、幂等性、所有权、限流和审计要求。
- 收集产品事件前，最小化数据并明确留存、同意和删除行为。

### SEO 与可发现性

- 维护公开内容路径的 canonical URL、社交元数据、robots 行为、404 正确性和稳定重定向。
- 对爬虫不可见的客户端标题，使用服务端或边缘渲染补充内容级元数据。

## 11. 度量与复盘节奏

### 阶段 0 建立基线

- 按发布版本和路由统计前端错误率。
- API 失败率和客户端可见重试率。
- 核心导航和内容渲染性能。
- Feed 订阅转化与首次阅读完成率。
- 编辑器恢复成功率和媒体导入完成率。
- 浏览器冒烟通过率与测试不稳定率。

### 每月产品复盘

- 复查阶段验收标准、用户反馈、事故数据和指标趋势。
- 移除没有可测用户或运营结果的工作。
- 只有当前工作可发布时，才重排下月优先级。
- 发布简短路线图更新，说明已完成、进行中、风险和优先级变化。

### 发布准入清单

功能只有满足以下条件才能进入发布：

1. 已知 API 契约与授权行为。
2. 已设计加载、空状态、错误、重试、权限和移动端状态。
3. 相关单测与浏览器场景通过。
4. 埋点和错误上报不暴露敏感内容。
5. 适用时已完成文档、feature gate、迁移与回滚行为。
6. 变更有明确负责人和用户可见发布说明。

## 12. 最近两个迭代的初始待办

1. 拆分并验证当前编辑器、路由、通知、Markdown 和设置改动的发布候选。
2. 定义官方托管和自托管前端的发布契约，并接入发布版本传播。
3. 在 CI 中增加最小浏览器冒烟工作流和夜间完整 Playwright 运行。
4. 产出测试覆盖率、Web Vitals 和错误上报基线。
5. 编写 Feed 分组规则 API 契约与前端交互设计。
6. 实现第一条包含预览、保存、可解释性和测试的 Feed 分组规则垂直切片。
7. 在实施排序改动前，定义搜索响应契约和相关性度量。
8. 审计 Studio 旧入口，并发布迁移和移除顺序。

## 13. 决策登记

以下决策必须在依赖阶段开始前确认：

| 决策 | 最晚需要时间 | 责任协作方 | 延迟后果 |
| --- | --- | --- | --- |
| Feed 是否是获客与日常使用的首要入口？ | 阶段 1 前 | 产品与工程 | 首个重大投入无法正确排序。 |
| 官方托管与自托管的发布通道分别是什么？ | 阶段 0 前 | 前端、后端、运维 | 部署、回滚和配置责任持续模糊。 |
| 允许采集哪些遥测数据，以及如何处理同意？ | 阶段 0 前 | 产品、安全、运维 | 无法安全衡量可靠性与转化。 |
| 公开增长前，哪些创作和社区动作必须接入审核？ | 阶段 2 前 | 产品、后端、运维 | 公开创作可能先于治理能力扩大。 |
| 公共 API 可接受的 scope 与限流规则是什么？ | 阶段 4 前 | 后端、前端、安全 | 无法安全构建扩展和外部集成。 |

## 14. 执行顺序

不可调整的交付顺序为：

1. 发布基线与运营清晰度。
2. Feed P0 与可测的日常使用闭环。
3. 创作流程与 Studio 收敛。
4. 共享媒体可靠性。
5. 外部生态、公共 API、扩展和跨设备能力。

可以提前研究后续阶段，但不得挤占当前阶段的验收标准。
