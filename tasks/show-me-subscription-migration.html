Subscription Model Repair

用模块订阅上下文修复跨模块分组冲突

保留全站统一的订阅目标，新增模块级归属记录。分组、提醒、排序和取消关注都作用于模块归属，而不是作用于全局订阅本身。

首期约束：同一订阅目标在同一个模块内可属于零或一个分组；跨模块可以属于不同分组。这个约束与现有单选分组交互一致，避免现在引入不必要的多分组成员关系。

1. 新的数据边界

目标去重与模块组织分别建模，所有跨模块行为才能可预测。

订阅目标频道 A、RSS 源等可关注对象的规范标识。唯一键：目标类型 + 目标 ID。
用户全局订阅表示用户仍关注该目标，用于“全部订阅”聚合与去重。唯一键：用户 + 订阅目标。
模块订阅上下文唯一键：全局订阅 + 模块。
播客 · A 分组提醒：开
视频 · B 分组提醒：静音

2. 必需的持久化与 API 合约

不要给旧的全局订阅记录继续增加特殊字段；新增上下文层，并令分组带模块作用域。

SubscriptionTarget

全站可订阅对象的规范引用。相同频道 A 不因为播客、视频各订一次而重复。

id target_type target_id

UserSubscription

用户对目标 A 的全局关注事实。中央订阅中心按这个实体聚合。

id user_id target_id UNIQUE(user_id, target_id)

ModuleSubscriptionContext

模块内的组织与设置。组、位置、静音、提醒、未读策略都放在这里。

id user_subscription_id module_key group_id? UNIQUE(user_subscription_id, module_key)

3. 频道 A 的行为应当是什么

每个动作只修改当前模块的上下文；全局记录仅在最后一个上下文移除时删除。

1在播客订阅频道 A，并放入 A 分组。
2在视频订阅频道 A，并放入 B 分组。
3把播客的频道 A 移到“通勤”分组。
4取消视频订阅频道 A。

最后的数据与界面结果

  • 全局订阅：频道 A 仍存在
  • 播客上下文：通勤分组
  • 视频上下文：已删除

中央订阅中心显示频道 A 的播客归属；视频侧栏不再显示频道 A；播客侧栏仍能按“通勤”筛选更新流。

4. 无中断迁移顺序

先兼容旧读写，再切换展示，最后移除旧字段。不能在一次发布中直接替换所有订阅数据。

Phase 1

扩展结构

新增目标、上下文与带 module_key 的分组表/字段，不删除现有订阅和书签接口。

Phase 2

回填与双写

旧通用订阅归为原 feed 上下文；播客 show bookmark 回填为 podcast 上下文。新操作同时写旧、新模型。

Phase 3

切换读取

中央订阅中心读聚合视图；播客和视频侧栏只读本模块上下文；对比新旧计数与采样数据。

Phase 4

收敛旧模型

停止旧字段写入，迁移旧 API 到兼容层；确认没有回滚需求后删除过时分组关联。

5. 上线前必须验证

这些用例能直接证明不会再出现跨模块分组覆盖。

必须通过的行为测试

  • 同一频道在播客 A 分组、视频 B 分组，两个侧栏各自正确显示。
  • 修改播客分组不会改变视频分组、静音或提醒。
  • 取消播客上下文后，视频上下文和全局订阅仍保留。
  • 删除最后一个模块上下文后，全局订阅才消失。
  • 中央订阅中心按一个目标聚合，并清晰展示各模块归属。

禁止发生的回归

  • 不要把模块名编码进分组名称，例如“播客/科技”。
  • 不要把频道 A 复制成两条无关联的全局订阅记录。
  • 不要用前端本地映射遮掩后端单一 group 字段。
  • 不要在未完成回填前删除 show-bookmarks 或旧订阅接口。
  • 不要因取消一个模块的订阅而静默取消其他模块。
建议确认

采用“全局订阅目标 + 每模块一个订阅上下文 + 每个上下文零或一个分组”的模型。确认后可以据此修订播客、视频与中央订阅中心的完整需求，并进入接口与迁移规格。
