Subscription Architecture Decision

全站订阅聚合，但分组必须属于模块上下文

频道 A 可以同时被用于播客和视频。用户在两个模块中的收听或观看场景不同，因此订阅事实可全局聚合，分组和设置却不能全局共享。

核心规则：一个“订阅目标”对应用户对频道 A 的关注事实；每个模块各自保存一条订阅上下文，分组、排序、静音和提醒都附着在上下文上。

当前风险：单一全局分组

订阅记录只有一个 subscription_group_id。

冲突：写入播客的 A 分组会覆盖视频的 B 分组，或产生两个无法识别为同一频道的重复订阅。

建议模型：全局目标 + 模块上下文

中央订阅中心汇总上下文，模块侧栏只取本模块。

订阅目标：频道 A用户关注的统一事实，避免重复来源

实现边界

这是数据模型与 API 合约的调整，不应靠前端筛选勉强修补。

  • 订阅目标：用用户与频道/RSS 源的唯一组合去重，作为全局聚合的父项。
  • 模块订阅上下文：唯一键为“用户 + 订阅目标 + 模块”；其中保存 group_id、位置、静音与提醒配置。
  • 模块分组：分组也带 module 作用域；同名的播客和视频分组不共享成员。
  • 取消关注：只删除当前模块上下文；只有最后一个上下文删除后，才删除全局关注事实。
  • 迁移：旧的单一分组归入原订阅模块；播客 show-bookmarks 映射为播客上下文，不覆盖既有视频归属。

需要确认的决策：采用“全局订阅目标 + 模块订阅上下文”的模型。确认后，播客侧栏的分组将只管理播客上下文；中央订阅中心会清楚展示频道 A 在播客 A 分组和视频 B 分组中的两个归属。
